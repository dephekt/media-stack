Fix these three first

Everything else is polish. These can crash the box or hurt the crop.

The 10-second version

  1. P1 Frequency = 0 crashes the controller in a boot-loop.
  2. A Home Assistant hiccup can leave the pump stuck ON (flood) or stall watering.
  3. There is no watering safety net overnight (P3) — the low-moisture alarm is never acted on.
High✓ Confirmed

Setting “P1 Frequency” to 0 crashes the controller — on a loop

The once-a-minute clock does minutes % P1_frequency to decide when to water. The P1 Frequency box lets you enter 0, and dividing by zero makes the ESP32 panic and reboot. Because that line runs every minute, it reboots again as soon as it comes back — a loop that only stops when you change the value.

Why it matters: one innocent-looking setting takes the whole controller offline — watering, dosing and sensors all dead — until it's corrected some other way.

Where & how to fix

Where: the time: minute-trigger lambda; number p1_frequency has min_value: 0.

Fix: guard the math — if (freq > 0 && minutes % freq == 0) — and set the number's min_value to 1 so 0 can't be entered.

High✓ Confirmed

A Home Assistant hiccup can leave the pump stuck ON — or stall watering

The pump is switched through a Home Assistant service, and after each on/off the script sits in a while loop waiting for HA to confirm the state — with no timeout. If Wi-Fi or HA drops right then, that loop spins forever: the irrigation script (single-run) never finishes, so no further shots happen. And if the pump was mid-shot when the link dropped, the turn-off path may never be reached — so it can stay energized.

Why it matters: a brief network blip can flood the tray or freeze watering for the rest of the day. This is the scariest one.

Where & how to fix

Where: p1event / p2event, the while: binary_sensor.is_off/is_on: ipump confirm-loops (no timeout, no api.connected re-check inside).

Fix now: add a retry cap / timeout to each loop, re-check api.connected inside it, and fail safe (assume off / abort) on timeout.

Better: drive the pump from a local relay (you have a spare) with an on-device max-run timeout, and just mirror the state to HA — no round-trip, no offline failure mode. More on this in the last section.

Medium✓ Confirmed

There's no watering during P3 — the overnight safety net never fires

You have a P3 Needs Water low-moisture flag (VWC ≤ P3 VWC Low Limit) — but nothing reads it, and vwc_check only has P0 and P2 branches. There is simply no code that waters during P3. So once you're in the overnight dryback, substrate can fall past your hard low limit and the controller just watches.

Why it matters: on a hot night an over-aggressive dryback can reach wilt territory with the safety you thought you had never triggering.

Where & how to fix

Where: vwc_check (P0 + P2 branches only); p3_needs_water is defined but consumed nowhere.

Fix: add a P3 branch to vwc_check that fires one emergency shot when p3_needs_water is true (still respecting auto_water / api.connected / maintenance mode).

Other correctness bugs

Real, but lower stakes — fix as you get to them.

Medium~ Verify

The daily schedule hinges on an exact one-second match (and may not even compile)

Lights-on/off and P2-close fire only when the clock string equals the set time to the exact second, in a one-minute window. If the device is rebooting or offline during that minute, the whole day's transitions are skipped. Separately: the to_string() used on the Home Assistant time text has no matching version in the ESPHome I checked — so either you're on a build where it exists, or this section doesn't compile at all.

Why it matters: the entire day cycle rides on a brittle one-second string match. Worth confirming it even builds.

Where & how to fix

Where: the time: trigger — str == to_string(id(lights_on_time).state).

Fix: stop string-matching. Use native time.on_time with at:, or drive transitions from the HA input_datetime directly. (This also sidesteps the to_string question entirely.)

Medium✓ Confirmed

A reboot near lights-on skips the daily counter reset

The daily shot counters zero out only inside the lights-on script — which is gated by that same one-second match, with no boot catch-up. Miss it (reboot / offline) and the counters stay where they were.

Why it matters: a stale p1_shot_count starts the day already "out of P1 shots," so the controller skips the P1 recharge ramp and jumps straight to P2.

Where & how to fix

Where: lightsonscript (number_to_min on the counters).

Fix: reset from an on_time at the configured time with a per-day "already reset" guard, or reconcile at boot from current-time vs lights-on.

Medium✓ Confirmed

Nutrient Pump C never runs, and dosing watches the wrong probe

The dosing loop pulses Pump A then Pump B — relay_5 "Nutrient C" is defined but never switched on anywhere, so a 3-part recipe silently drops part C. And the loop decides based on EC2, which is the conductivity of a soil probe, not your reservoir — so it's chasing a signal that lags reservoir changes badly.

Why it matters: wrong nutrient ratios (A/B only), and dosing that either never converges or reacts to the wrong thing — mis-fertilization.

Where & how to fix

Where: nutrient_dosing_script (only relay_3/relay_4 fire; condition reads id(EC2).state).

Fix: add a Pump-C step (or document that it's intentionally 2-part), and regulate on a dedicated reservoir EC sensor rather than the substrate probe.

Medium~ Plausible

“Field capacity” can lock in too early on a fresh start

On a new or factory-reset device field_capacity starts at 0, which makes one of the detection guards (field_capacity − VWC ≤ 10) always true. So first-cycle field capacity can be declared off a bad baseline once you're past half your shots.

Why it matters: an under-estimated field capacity skews your P2 targets and dryback math for the whole run. (A sibling guard gives some protection, so impact depends on your dynamics — hence "plausible.")

Where & how to fix

Where: p1event, second if block; field_capacity seeded from the 0-initialised global.

Fix: require field capacity to be validly set before that guard counts, and gate the first-ever detection on an absolute saturation criterion.

Medium✓ Confirmed

The end-of-day shot isn't confirmed but still counts

Unlike the P1/P2 shots, the P3-start shot fires on/off with no pump confirmation and no api.connected guard — then increments the shot counters regardless of whether the command actually landed.

Why it matters: a dropped command means no water but a counted shot (or an unverified turn-off), corrupting the day's accounting and water estimate.

Where & how to fix

Where: startP3, the p2_end_shot branch.

Fix: reuse the confirmed on/off pattern (with a timeout), and increment counters only after a confirmed run.

Medium✓ Confirmed

Long waits inside single-run scripts silently drop needed shots

Every script is mode: single. p2event ends with a blocking delay of up to the whole P2 frequency (minutes → hours) used as the spacing timer. While it's parked there, any genuinely-needed shot is dropped rather than queued, and the whole timer is lost if the device reboots mid-window.

Why it matters: irrigation timing degrades quietly — the "frequency" is a fragile blocking delay, not a real schedule.

Where & how to fix

Where: p2event trailing delay: p2_frequency*60*1000; caller vwc_check.

Fix: track "next-allowed-shot" as a timestamp/global and gate on it, instead of holding the script open. Consider mode: queued where re-entry should count.

Quick cleanups — where the “insane to manage” feeling actually comes from

No behavior change; these are the maintainability wins.

Housekeeping
  • Stop logging every line into a sensor. logger is at VERBOSE and every log line is published into a Home Assistant text_sensor — that's API + recorder spam and a truncated, near-useless "log." Drop it; run at INFO and use the web/OTA log stream.
  • De-duplicate the copy-pasted math (biggest win). The VPD formula is hand-copied 6× (and the constants have already drifted between copies), and the P1/P2 shot-time & volume math is duplicated 4×. Collapse each into one !include fragment so a fix happens once.
  • Trim persistence. Keep restore_value: true on real config (targets, tolerances, steering phase) but not on per-cycle counters — you pay flash wear without reliable persistence.
  • Delete dead weight: logger tags that match no component, the unused rs232 UART and spi bus, and the disabled TDS sensors. If the DAC "dimmers" drive a linear 0–10 V buffer, set gamma_correct: 1.0.

“Is it insane to manage? Should I make it a component?”

The honest answer, and what I'd actually do.

Don't rewrite it as a custom C++ component.

The pain here is one 2000-line file with copy-pasted logic — not a limitation of ESPHome. A C++ component is the most work for the least payoff:

  • It can't act on its own anyway. The pump, the clock, the lights/P2 times, and the maintenance switch all live in Home Assistant, and the scripts already stop when HA is unreachable. So an on-device C++ "brain" still can't water or dose if HA is down — the usual reason to embed a state machine doesn't apply.
  • It's the heaviest option. A faithful component is a several-hundred-line Python + C++ project (ESPHome's own sprinkler and thermostat components are simpler than this), with build breakage on ESPHome updates and slow reflash-cycle debugging — the exact pain you already feel with the pinned mod_ph component.
  • You'd lose live tuning. Every dashboard slider would have to be re-plumbed as a schema field and re-exposed — re-implementing what template numbers give you for free.

What I'd do instead

  1. Now (biggest relief, low effort): split the monolith into ESPHome packages: / !include files by concern (board+buses · environment/VPD · soil VWC+EC · dosing · irrigation state machine · HA entities), and collapse the duplicated VPD / shot math. Pure ESPHome, no toolchain, still fully dashboard-tunable. Fix the Tier-1 bugs in the same pass. This resolves most of the "insane" feeling by itself.
  2. Later (optional): since it's already HA-centric, move the slow phase logic into Home Assistant — Node-RED for a visual state machine, or pyscript/AppDaemon for real Python with history and logs — and leave ESPHome as a clean sensor + relay node. Keep thin on-device safety (local-relay pump with a max-run watchdog, max-dose ceiling, float-switch cutoff) so a network blip can never overdose or leave the pump on.

A custom component is at best worth it for one or two genuinely awkward helper calculations — never for the whole brain.
